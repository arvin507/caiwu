## 新增发票号码去重（防重复落库）
- 需求：同一张发票（按发票号码）不能多次落库；解析出号码若已存在，则删除本次上传并提示用户。
- 设计：在上传落库**前**先同步解析拿发票号码，再查重；命中则不建记录并 `unlink` 落盘文件，记入 `skipped`；未命中才建记录并直接写入 parsedData（parseStatus 同步 done/failed）。
  - 选同步解析（而非旧版异步）是因为去重必须先拿到号码才能决定是否插入，且本地 PDF/OFD 解析是毫秒级、图片 OCR 也是几百 ms，本地项目可接受。顺带取消了原先的「建记录→异步解析」写法，响应里直接带 parsedData。
- 改动文件：
  - `backend/src/app/api/invoices/route.ts`：POST 改为「落盘→解析→去重→建记录」循环；查重用 Prisma JSON 路径过滤 `{ parsedData: { path: 'invoiceNumber', equals: invoiceNumber } }`（`path` 必须是 string 顶层键，数组写法在本机 Prisma 类型下报 TS2322）；响应由 `Invoice[]` 改为 `{ created, skipped }`。新增 `unlink` 导入。
  - `src/store/useAppStore.ts`：`addInvoices` 返回类型改为 `{ created, skipped }`，合并 created 进列表。
  - `src/pages/Invoices/UploadModal.tsx`：`onFinish` 处理 created/skipped——成功提示存档张数，重复发票用 `message.warning` 列出「文件名（号码 X）」，并更新去重注释。
- 限制：仅当解析能抽出 invoiceNumber 时才能去重；图片未配百度 OCR 或扫描件抽不出号码时无法去重（按失败落库），前端有「人工核对」兜底。批量同一次请求内若含两张相同号码，第一张落库、第二张被跳过（顺序处理无竞态）。
- 前后端 tsc 均通过（后端 EXIT=0；前端仅残留项目原有 `tsconfig.app.json` 的 `baseUrl` 弃用告警，非本次改动）。

## 修复：MySQL JSON path 去重查询 500（错误码 3143）
- 现象：上传发票时后端 500，报错 `ConnectorError ... code: 3143, "Invalid JSON path expression"`，发生在 `prisma.invoice.findFirst({ where: { parsedData: { path: 'invoiceNumber', equals } } })`。
- 根因：Prisma 在 **MySQL** 上对 Json 字段用 `path` 过滤会生成非法 JSON path，MySQL 8 直接拒绝（position 1）。该写法在 SQLite/Postgres 可能 OK，但 MySQL 不行。
- 修法（更稳、可索引）：放弃在 JSON 内查，给 `Invoice` 加独立列 `invoiceNumber String?` + `@@index([invoiceNumber])`；去重改 `where: { invoiceNumber }`；建记录时把号码写入该列。
- 复用提醒：**Prisma + MySQL 下不要用 Json 字段的 `path` 过滤做查询（含 findFirst/where/update），一律改用独立列或使用 Prisma raw query。** 已同步加 `invoiceNumber` 到前端 `src/types/index.ts` 的 Invoice 类型。
- 用户侧动作：`cd backend && pnpm prisma db push`（会顺带 generate client），再重启后端 `pnpm dev`。沙箱里 `prisma generate` 因引擎文件被本机运行中的后端占用报 EPERM，但 tsc 已 EXIT=0 证明类型正确；用户本机可正常 generate。
