## 修复 P2000：parseError 列太短导致上传 500
- 现象：真实 `POST /api/invoices` 上传失败，Prisma 报 `P2000`（Column: parseError），`prisma.invoice.create`(route.ts:141) 抛 500。是本地 OCR 接入后「created 分支未充分实测」暴露的漏洞。

  1. schema：`parseError` / `note` 改 `String? @db.Text`；`prisma db push` 已同步 DB。
  2. `local_ocr.py`：`__main__` 包 try/except，异常只输出简短 `OCR_ERROR: <类型>: <信息>`（不再全 traceback）。
  3. `localOcr.ts`：失败错误信息 `slice(0,1000)` 兜底。
- 验证：`tsc` OK；真实上传不支持的 `.txt` 触发解析失败，返回 201（此前 500），`parseStatus:"failed"` + 简短 `parseError` 正确落库。
- 教训：MySQL 下 Prisma `String` 默认 `varchar(191)`，错误/自由文本/OCR 原文类列必须显式 `@db.Text`；引擎层异常输出简洁错误而非全 traceback。

## 火车票票价 OCR 误识 `62_00`（小数点变下划线）导致解析失败 — 已修复
- 现象：用户贴的火车票 `票价：￥62.00` 被 OCR 识别成 `62_00`，原票价正则 `(\d+\.\d{2})` 匹配失败 → `totalAmount=None` → 解析失败（与之前火车票完全没适配是同类「缺字段/失败」问题）。
- 根因 & 修复（`backend/local_ocr.py`）：
  - 新增 `_normalize_amount(raw)`：先把全角数字归一化，再把小数点误识的 `_`/`,`/`·`/`。`/`．` 统一成 `.`，`1,234.00` 视 `,` 为千分位去掉；正则 `(\d+)(?:\.(\d{1,2}))?` 解析，小数位 1 位（十分位）**向右补 0**（`ljust(2,'0')`），不能用 `zfill`（左补会把 `137.5` 错成 `137.05`）。
  - 新增 `_extract_amount_from_line(text)` + `_AMOUNT_RE = \d+(?:,\d{3})*(?:[._,·。．]\d{1,2})?`：优先取含小数的金额、纯整数兜底。火车票票价抽取改用它（之前是严格 `(\d+\.\d{2})`）。
  - **扫描同类位置并一起修**：增值税路径 `extract_amount_with_tax`（价税合计/小写行）和 `extract_detail_amounts`（金额/税额候选）原来也是 `(\d+\.\d{2})`，同样会被 `62_00` 击穿 → 全部改用 `_extract_amount_from_line`。否则增值税票的金额/税额也会因 OCR 小数误识而解析失败。
- 验证：① 单元/集成测试（`_normalize_amount` 各噪声变体 + `parse_train_ticket` + VAT 价税合计配对）全部正确（`62_00`→`62.00`、`55_36`→`55.36`+`6_64`→`6.64` 配对出 amount/tax、`1,234.00`→`1234.00`、`137．00`→`137.00`）。② **真实 API 端到端**：生成含字面 `票价：￥62_00` 的火车票 PDF（msyh.ttc 渲染），`POST /api/invoices` 上传 → `parseStatus:done`、`totalAmount:62.00`、`invoiceType:train`、各字段正确。该发票号 `26339190041008728512` 此前已由用户真实上传过且解析失败，按发票号去重**就地更新**为正确结果（复用用户原存储文件，未动真实文件；fileName 已改回规范名 `铁路电子客票_...pdf`）。清理了测试 PDF/脚本。
