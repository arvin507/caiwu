## 修正：「选文件不显示 + 点存档没反应」是真 bug，非 stale tab（13:40 复查）
上一轮把用户反馈的「选文件不显示/点存档没反应」都归为 stale tab，是误判。**真实根因是前端 UploadModal 的代码 bug**：
- `<Upload fileList={fileList}>` 用的是**受控模式**，但代码只调了 `customRequest` 里的 `options.onSuccess` 和 `setSelected`，**从未通过 `onChange` 把选中文件同步回 `fileList` state**。
- antd v6 受控 Upload：传了 `fileList` 它就只显示你给的内容，自己不会往里加文件 → 所以「选了文件界面啥也不显示」。
- 连带影响：用户看到没文件、以为没附上，加上可能在跑旧页面，「点存档没反应」被放大。后端（curl 直连 / 经代理 8787→写盘 server/uploads/*.png→返回 fileUrl）早已验证全通，与本 bug 无关。

**修复**（UploadModal.tsx）：
- 新增 `onChange`：`setFileList(info.fileList.filter(f=>f.status!=='error').slice(-1))` 把内部状态同步回受控 fileList（核心修复，解决"不显示"）。
- 文件 Form.Item 加 `required` + `validateStatus/help`（无文件时红字提示"请选择发票文件"），让"没选就点存档"给出明确反馈。
- `onFinish` 兜底 `if(!selected) message.error('请先选择发票文件')` 保留。
- 验证：curl 直连 POST 上传 → 后端 201 + server/uploads 0→1 落盘，删测试记录后回 0，证明后端无问题；前端改动属受控组件同步逻辑，无需编译（用户约定改完不编译）。Vite HMR 会自动热更新，用户需**硬刷新一次**确保加载最新代码。

**经验纠正**：用户给出"选了文件不显示"这种具体 UI 现象时，应优先查前端组件状态同步（受控组件的 onChange 回写），而不是默认甩锅 stale tab。stale tab 只是叠加因素。

**关键发现（重要，排查 DELETE 删不掉文件）**：
- 现象：DELETE 返回 `{ok:true}` 且库记录删除成功，但 `backend/uploads/` 磁盘文件残留。
- 排查：先手动 `node -e unlink(...)` 用相同路径**能成功删除**（证明路径逻辑正确）；后在 DELETE 的 catch 里把真实错误塞回响应 → 得到 `[safe-delete][SAFE_DELETE_BULK_REJECTED] ... targets:[.../backend/uploads/inv-*.pdf]`。
- **根因 = 本 AI 沙箱环境的「安全删除保护」(safe-delete) 拦截了服务端进程里的 `fs.unlink`**（与之前它拦 Next.js 清 `.next` 缓存同一机制）。手动 shell 删除不受此拦截，但服务端代码内的删除被拦。
- **结论**：DELETE 接口代码本身完全正确，部署到普通机器/服务器 `unlink` 会正常生效；当前环境删不掉文件纯属沙箱策略限制，非代码 bug。
- 注意：用户在删除残留文件时**拒绝了**权限请求，故 `backend/uploads/` 下残留的孤儿 pdf 暂不清理，待用户在普通环境运行或手动处理。
- 教训：服务端"静默失败"的 catch 是排查噩梦——应 `console.error` 记录而不是 `catch{}` 吞掉（已修正）。
