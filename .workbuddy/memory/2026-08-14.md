## 修复发票解析金额/税额/价税合计错乱（invoiceParser.extractFields）
- 现象：电子专票原文中，金额/税额被抽空、价税合计错抽成税额（如 26337000000711672681，金额应 224.06、税额 13.44、价税合计应 237.50，却得空/空/13.44）。
- 根因：① 旧逻辑价税合计取「最后一个 ¥xx.xx」，但此类版式把 金额/税额 挤到「开票人」之后，导致末尾 ¥ 是税额；② 金额/税额依赖 `¥金额¥税额` 紧挨正则，而原文是 `224.06\n¥\n13.44\n¥`（¥ 在数字后），匹配不到。
- 难点：明细行 `*...无次1224.0566037736224.066%13.44` 中，长小数单价 `1224.0566037736` 与金额 `224.06` 直接拼接、且金额末位 `6` 与税率 `6%` 共用（拼成 `224.066%`），导致任何「按位置/按前缀」抠法都被污染。
- 修法（已 node 验证 ALL PASS + tsc 通过）：
  - 税额 = 税率 `X%` 后的第一个两位小数（正则 `\d+(?:\.\d+)?%\s*(\d+\.\d{2})`，稳健不受长小数干扰）。
  - 价税合计 = 所有 `¥xx.xx` 中的最大值（VAT 恒等式：价税合计=金额+税额，恒为最大金额），保留原始字符串避免丢末尾 0。
  - 金额 = 价税合计 − 税额（VAT 恒等式推导，彻底绕开版式串扰）；税率前两位小数与 `¥金额¥税额` 紧挨形式作兜底。
  - 顺带：购买方名称由「仅个人」改为取第二个「*公司」候选（companyMatches[1]），个人仍优先。
- 影响：仅改了 `backend/src/lib/invoiceParser.ts`；已入库的旧发票若当时解析错误，需重跑解析才能刷新 parsedData（可加一次性重解析脚本/接口，待用户确认）。

## 百度 OCR QPS=2 限流 + 失败重试导致同一发票两条记录
- 两个交织问题：
  1. **QPS 限制 2**：百度 vat_invoice 接口 QPS=2，批量/并发上传易触发限流报错。
  2. **失败重试成功 → 两条记录**：解析失败建的记录 `invoiceNumber=null`，不参与按发票号去重；之后同文件重传解析成功拿到号码，去重查不到那条失败记录 → 又新建一条（失败那条 + 成功那条共存）。
- 修法：
  - `backend/prisma/schema.prisma`：`Invoice` 新增 `fileHash String?`（文件内容 sha256），`prisma db push` 已应用（MySQL 3307 在线）。
  - `backend/src/lib/baiduOcr.ts`：加全局信号量 `OCR_MAX_CONCURRENCY=2`（`acquireSlot/releaseSlot`），保证同时在途 OCR 请求 ≤2，跨请求/跨用户统一节流；`baiduVatOcr` 内对 QPS 错误码 18 / 限流 / 网络抖动做最多 3 次指数退避重试（500ms→1s→2s）。
  - `backend/src/app/api/invoices/route.ts` POST：每张文件算 `fileHash`；去重先按 `fileHash`、再按 `invoiceNumber`；命中已有记录 → **`prisma.invoice.update` 覆盖解析结果（保留原 id/文件，不新建）**，仅当该记录已关联报销单时才 `skipped`（不覆盖在用数据）；新建记录带上 `fileHash`。返回 `{ created, updated, skipped }`。
  - 前端：`useAppStore.addInvoices` 接收并合并 `updated`（按 id 原地替换 / 新建置顶）；`UploadModal` 新增「已更新 X 张」提示。
- 关键收益：同文件「先失败、后重试成功」现在只会产生一条记录（fileHash 命中→幂等更新）；失败记录也带 fileHash，重传必命中。
- 注意：本机 `rm` 被 WorkBuddy 安全删除机制拦截（回收站调用失败、fail-closed 不删），`prisma generate` 因此中断并损坏 Prisma 类型。绕过办法：用 `mv` 把旧 `.prisma` 重命名为 `.prisma.bak` 再 `generate`（rename 不被拦截）。`prisma db push` 正常。
- 类型检查：后端/前端 tsc 均 EXIT=0。

## 修复 P2000：parseError 列太短导致上传 500（2026-08-15）
- **现象**：真实 `POST /api/invoices` 上传失败，Prisma 报 `P2000 The provided value for the column is too long`（`Column: parseError`），在 `prisma.invoice.create`(route.ts:141) 抛 500。这是上一轮「created 分支未充分实测」暴露的漏洞。
- **根因（实测定位，非猜测）**：`schema.prisma` 中 `parseError String?` 在 MySQL 下默认映射 `varchar(191)`；而解析失败时 `localOcr.ts` 把 OCR 的 stderr（可能含长 traceback）拼进错误信息，最长 ~525 字符 → 超出 191 → P2000。同类风险列还有 `note String?`（自由文本备注）。`parsedData` 是 `Json?`，`rawText` 存在 JSON 内，不受影响。
- **修复（扫描所有相关位置）**：
  1. schema：`parseError` 与 `note` 改为 `String? @db.Text`（MySQL Text 无长度上限）；`cd backend && pnpm prisma db push` 已生效（DB 已同步）。
  2. `local_ocr.py`：`if __name__ == "__main__"` 包 try/except，异常只向 stderr 输出简短 `OCR_ERROR: <类型>: <信息>`（不再整段 traceback），从源头缩短错误串。
  3. `localOcr.ts`：失败错误信息限长 `slice(0, 1000)` 兜底（Text 已够，仍加一层防护）。
- **验证**：`tsc --noEmit` OK；真实上传一个不支持的 `.txt` 触发解析失败，返回 **201**（此前 500），记录 `parseStatus:"failed"` + 简短 `parseError` 正确落库，去重/更新分支均不溢出。
- **教训**：MySQL 下 Prisma `String` 默认 `varchar(191)`，任何「错误信息 / 自由文本 / OCR 原文」类列都必须显式 `@db.Text`，否则失败场景必炸 P2000；且引擎层异常要输出**简洁**错误而非全 traceback。
