## 一、两类报销单的差异（决定表结构）

实测两份模板后确认结构差异很大：

| | 差旅费报销单 | 一般费用报销单 |
|---|---|---|
| 头部 | 部门/项目/出差事由/日期/出差人/起止时间/起止地点/人数 | 公司/申请人/部门/项目/凭证编号/申请日期 |
| 明细 | **两段式**：①行程段（每段一行：日期/交通/发站/到站/金额小计/单据）②费用汇总段（住宿费/伙食/其他…） | **单一列表**：序号/摘要/费用类型/金额/备注 |
| 金额特点 | 行程段金额是干净单值；费用汇总段按「千/百/十/元/角/分」**分列填** | 金额是干净单值 |
| 合计 | 行程段合计 + 费用汇总段合计 | 明细求和 |

核心结论：**两类单「骨架」相同（谁申请/报多少/什么状态/附什么文件/谁批），「明细形状」不同**。

## 二、数据表设计（主表 + 差旅专用子表）

采用「主表共用 + 明细按类型挂子表」，一套流程管两种单，又不丢差旅特有信息。

```
Reimbursement (主表, travel/general 共用)
   │ 1—*  ReimbursementItem        ← 一般费用明细 / 差旅费用汇总段 都用
   │ 1—1  ReimbursementTrip        ← 仅 type='travel' 有（出差信息）
   │ 1—*  ReimbursementTripLeg     ← 仅 type='travel' 有（行程段，每行一段）
```

**Reimbursement**（共有骨架）
- `type` travel | general
- `applicantName` 申请人（解析自 Excel）
- `department` / `projectName` / `projectCode` / `applyDate`
- `totalAmount` Decimal(10,2) —— **由明细求和得出，不信任手写大写**
- `status` draft → submitted → approved / rejected → paid
- `storagePath` / `fileName` —— 原始 xlsx 落盘路径（文件存 `backend/uploads/`，库只存路径）
- `submitterId` / `approverId` / `approvedAt` / `rejectReason`

**ReimbursementItem**（通用明细）
- `seq` / `category`（费用类型）/ `summary`（摘要）/ `amount` Decimal / `note`
- 一般费用直接用；差旅的「费用汇总段」也复用它

**ReimbursementTrip**（差旅专用，一对一）
- `travelerName` / `startDate` / `endDate` / `fromLocation` / `toLocation` / `headcount` / `reason` / `dateRangeText` / `locationText`

**ReimbursementTripLeg**（差旅专用，一对多）
- `legDate` / `transport` / `fromStation` / `toStation` / `amount` Decimal / `ticketCount`

> 金额一律用 `Decimal(10,2)`，明细 `onDelete: Cascade` 跟随主表删除。
> 迁移命令：`pnpm db:push`（已执行，4 张表已建到 MySQL）。

## 三、业务流程（推荐方案）

```
① 上传  POST /api/reimbursements  (multipart: type + file)
   后端：先解析(内存) → 失败直接 400 不落盘 → 成功则落盘 uploads/ + 写库(status=draft)
② 列表  GET  /api/reimbursements        （admin 看全部，普通用户只看自己）
   详情  GET  /api/reimbursements/:id    （含 items/trip/legs）
   预览  GET  /api/reimbursements/:id/file（在线看原始 xlsx）
③ 用户核对/手改草稿 → 确认提交
         PATCH /api/reimbursements/:id/status  {action:"submit"}   draft→submitted
④ 管理员审批
         {action:"approve"}  submitted→approved  （记录 approverId/approvedAt）
         {action:"reject", reason}  submitted→rejected
         {action:"paid"}     approved→paid
```

要点：
- **上传即落库为 draft**，刷新不丢、可断点继续；提交是独立动作，防止误提交。
- **合计由系统对明细求和**，手写大写仅作展示，避免模板填错带偏数据。
- **权限**：列表/详情/预览按角色过滤（admin 全量，普通用户仅自己的）；`approve/reject/paid` 仅 admin（`requireAdmin` 守卫）。

## 四、接口清单

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| POST | `/api/reimbursements` | 上传 xlsx + 解析 + 落库 draft | 登录 |
| GET | `/api/reimbursements` | 列表（角色过滤） | 登录 |
| GET | `/api/reimbursements/:id` | 详情（含子表） | 本人/admin |
| GET | `/api/reimbursements/:id/file` | 预览原始文件 | 本人/admin |
| DELETE | `/api/reimbursements/:id` | 删除（级联删子表） | 本人/admin |
| PATCH | `/api/reimbursements/:id/status` | 状态流转 | submit=本人；其余=admin |

请求示例：
```bash
# 上传（type 必填：travel | general）
curl -X POST http://localhost:4000/api/reimbursements \
  -H "Authorization: Bearer $TOKEN" \
  -F "type=travel" -F "file=@差旅费报销单.xlsx"

# 状态流转
curl -X PATCH http://localhost:4000/api/reimbursements/$ID/status \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"action":"submit"}'
```

## 五、Excel 解析要点（`src/lib/reimbursementParser.ts`）

- 用 `exceljs` 读 xlsx；按 `type` 路由到差旅/一般解析器，未指定时自动识别（标题含「差旅」即为差旅）。
- **合并单元格**：值落在合并区最后侧列，读取时注意坐标偏移。
- **分列金额**：差旅费用汇总段的报销金额按「千/百/十/元/角/分」分列且**右对齐**（如 600 写作 `6,0,0,0,0`），解析时收集非空单元格、左侧补零后按位加权还原。
- **Excel 日期序列号**：`日期` 列存的是序列号（如 46204）而非文本，需转成 JS Date 取年份；模板里未填的头部字段只会显示标签文本（如「所属项目」），解析时识别为空。
- **金额用字符串传给 Decimal**：`String(amount)`，避免 JS 浮点误差。
- 解析结果先存为 draft 交用户核对，模板变动/解析异常可手改。
