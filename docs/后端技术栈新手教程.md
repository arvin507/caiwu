# 后端技术栈新手教程（caiwu 财务系统）

> 适用对象：刚接触后端、想搞懂"这个 `backend/` 目录里到底在搞什么"的同学。
> 目标：用大白话把后端用到的每一个技术、每一个文件、每一次请求怎么流动，讲明白。
> 配套：前端怎么跑、怎么登录，见根目录 `README.md`；整套项目从零讲起，见 `docs/新手教材-财务系统从零到实战.md`。

---

## 第 1 章 后端到底是个啥（类比）

想象一家餐厅：

- **前端** = 菜单 + 服务员。顾客（浏览器）看菜单点菜，服务员把单子送进后厨。
- **后端** = 后厨 + 收银台。它接收订单、真正"做菜"（处理业务逻辑）、把结果端出来。
- **数据库（MySQL）** = 餐厅的冰箱和仓库。食材（数据）真实存在这里，后厨按需要存取。

你打开网页点"上传发票"，浏览器并不会自己存发票——它把文件和数据**发给后端**，后端存到数据库，再回一句话"存好了"。这就是后端存在的意义：**保管数据 + 执行业务规则 + 给前端发数据**。

本项目里，后端代码全在 `backend/` 这个文件夹。

## 第 2 章 后端用到的技术栈全景

| 技术 | 角色（一句话） | 类比 |
| --- | --- | --- |
| **Next.js 15**（App Router） | 后端框架：一个文件 = 一个接口 | 后厨里的一个"工位"，专门处理某类订单 |
| **TypeScript** | 给数据上"类型保险" | 菜谱上写清楚"加盐 5 克"，不写错单位 |
| **Prisma 6**（ORM） | 让你用 TS 对象操作数据库，不用手写 SQL | 一个翻译官，把"我要查用户"翻成数据库听得懂的话 |
| **MySQL 8.0** | 真正存数据的关系型数据库 | 餐厅的冰箱/仓库 |
| **bcryptjs** | 把密码变成"不可逆密文" | 把钥匙熔掉只留锁的形状，谁也看不到原钥匙 |
| **jsonwebtoken (jwt)** | 登录后发一张"通行证" token | 进园区的工牌，下次刷一下就知道你是谁 |
| **tsx** | 让 Node 能直接跑 `.ts` 脚本 | 让不识字（不懂 TS）的厨师也能照着 TS 菜谱做 |
| React 19 / react-dom | Next.js 自带（本项目后端只用了它的类型与根页面） | 顺带送的，本项目 API 本身不依赖它 |

> 一句话总结：**Next.js 当框架搭架子，Prisma 当翻译操作 MySQL，bcrypt 管密码，jwt 管登录，TypeScript 全程兜底不出错。**

## 第 3 章 逐个技术讲

### 3.1 Next.js 的 Route Handlers（最核心）

传统后端要装 Express、自己配路由。Next.js 15 的 **App Router** 用一种"约定优于配置"的方式：**在 `app/api/某路径/route.ts` 里写文件，这个文件就自动变成一个接口**。

看本项目的真实文件：

```
backend/src/app/api/
├─ health/route.ts              → GET  /api/health
├─ auth/
│  ├─ login/route.ts            → POST /api/auth/login
│  ├─ me/route.ts               → GET  /api/auth/me
│  └─ change-password/route.ts  → POST /api/auth/change-password
├─ invoices/
│  ├─ route.ts                  → GET/POST  /api/invoices
│  └─ [id]/
│     ├─ route.ts               → GET/DELETE /api/invoices/:id
│     └─ file/route.ts          → GET  /api/invoices/:id/file
└─ users/route.ts               → GET/POST /api/users
```

每个 `route.ts` 里，你导出一个和 HTTP 方法同名的大写函数就行了：

```ts
// backend/src/app/api/health/route.ts（真实代码）
import { NextResponse } from 'next/server'
export async function GET() {
  return NextResponse.json({ status: 'ok', service: 'caiwu-backend' })
}
```

- `GET` 函数 → 处理 GET 请求
- `POST` 函数 → 处理 POST 请求
- 返回用 `NextResponse.json(...)`，自动变成 JSON 响应

**`[id]` 是什么？** 中括号表示"动态参数"。`/api/invoices/abc123` 里的 `abc123` 会被塞进 `params.id`。注意 **Next.js 15 里 `params` 是个 Promise**，所以要 `await`：

```ts
// backend/src/app/api/invoices/[id]/route.ts（节选）
export async function GET(
  _req: NextRequest,
  { params }: { params: Promise<{ id: string }> },
) {
  const { id } = await params          // ← 必须 await
  const inv = await prisma.invoice.findUnique({ where: { id } })
  ...
}
```

### 3.2 TypeScript：类型保险

后端代码里到处是 `req: NextRequest`、`{ userId: string; role: string }` 这种标注。意思是"这个函数接收的东西长这样"。写错了字段名、传错类型，编辑器/编译期就拦你，比运行时才报错安全得多。

### 3.3 Prisma：数据库的翻译官（ORM）

你**不用写 SQL**。想查一个用户，写成：

```ts
const user = await prisma.user.findUnique({ where: { username: 'admin' } })
```

Prisma 会帮你翻译成 `SELECT * FROM users WHERE username = 'admin'`。好处：
1. 不写 SQL，少犯错；
2. 换数据库（比如 MySQL 换 SQLite）几乎不改业务代码；
3. 有类型提示，表字段名拼错立刻红。

三个关键动作（都在 `package.json` 的脚本里）：
- `prisma generate`：根据 schema 生成"翻译官代码"（装依赖时 `postinstall` 会自动跑）。
- `prisma db push`：按 schema 直接把表结构同步到数据库（本项目用这个，简单）。
- `prisma db seed`：灌初始数据（本项目创建默认管理员 `admin/123456`）。

### 3.4 MySQL：真正的仓库

数据最终存在这里。本项目用 Docker 起一个 MySQL 容器（见 `docker-compose.yml`），数据库名 `caiwu`，账号 `root/caiwu123`，宿主机端口 `3307`。

### 3.5 bcryptjs：密码不能明文存

**永远不要把密码原文存数据库**。本项目存的是 bcrypt 哈希：

```ts
// backend/src/lib/auth.ts（真实代码）
export async function hashPassword(pw: string): Promise<string> {
  return bcrypt.hash(pw, 10)        // 10 是"加盐成本"，越大越安全也越慢
}
export async function verifyPassword(pw: string, hash: string): Promise<boolean> {
  return bcrypt.compare(pw, hash)   // 比对明文和哈希是否匹配
}
```

同样的密码，每次哈希结果都不同（因为自动加盐），但 `compare` 能正确判断"是不是这个密码"。原密码谁也看不到。

### 3.6 jsonwebtoken：登录发通行证

用户登录成功后，后端签一张 token（工牌）给他：

```ts
// backend/src/lib/auth.ts（真实代码）
export function signToken(payload: JwtPayload): string {
  return jwt.sign(payload, JWT_SECRET, { expiresIn: '7d' })  // 7 天有效
}
```

之后前端每次请求都在请求头带 `Authorization: Bearer <token>`。后端用 `verifyToken` 解开，就知道"这是谁、什么角色"，不用每次都查密码。

> 注意：token 里只放 `userId` 和 `role` 这种非敏感信息，绝不放密码。

### 3.7 tsx：跑 TypeScript 脚本

`prisma/seed.ts` 是 `.ts` 文件，Node 默认看不懂。用 `tsx` 包一层就能直接跑（`package.json` 里 `"seed": "tsx prisma/seed.ts"`）。

```
└─ package.json         # 依赖 + 命令脚本
```

### 4.1 `src/lib/prisma.ts` —— 单例，别小看

```ts
const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient }
export const prisma = globalForPrisma.prisma ?? new PrismaClient()
if (process.env.NODE_ENV !== 'production') {
  globalForPrisma.prisma = prisma
}
```

为什么这么绕？因为开发时 Next.js 会频繁"热重载"，如果每重载一次就 `new PrismaClient()`，数据库连接会越积越多直到爆掉。用 `globalThis` 缓存一份，全局复用，就稳了。**这是 Next.js + Prisma 的标准写法，记住即可。**

### 4.2 `src/lib/auth.ts` —— 鉴权工具箱（重点）

这个文件把所有"和登录/权限相关"的逻辑集中起来，其它接口直接调用：

| 函数 | 作用 |
| --- | --- |
| `hashPassword(pw)` | 明文 → 密文 |
| `verifyPassword(pw, hash)` | 校验密码对不对 |
| `signToken(payload)` | 发 token（7 天有效） |
| `verifyToken(token)` | 验 token，失败返回 `null` |
| `getBearer(req)` | 从请求头取 `Bearer xxx` |
| `getCurrentUser(req)` | 解析 token → 查库拿到最新用户（含 role） |
| `requireAdmin(req)` | 管理员守卫：未登录返回 401、非 admin 返回 403、通过返回 `null` |
| `toPublicUser(user)` | 脱敏：去掉密码哈希，只留能公开的字段 |

`requireAdmin` 的用法很巧妙——它"要么返回错误响应，要么返回 null"：

```ts
// backend/src/app/api/users/route.ts（真实代码）
export async function GET(req: NextRequest) {
  const denied = await requireAdmin(req)
  if (denied) return denied          // 有错误就直接返回，终止
  // 往下就是"已确认是管理员"的逻辑
  const users = await prisma.user.findMany({ ... })
  return NextResponse.json(users)
}
```

### 4.3 接口文件逐个看

**登录 `auth/login/route.ts`**
```ts
const user = await prisma.user.findUnique({ where: { username } })
if (!user || !(await verifyPassword(password, user.passwordHash))) {
  return NextResponse.json({ error: '用户名或密码错误' }, { status: 401 })
}
const token = signToken({ userId: user.id, role: user.role })
return NextResponse.json({ token, user: toPublicUser(user) })
```
注意：**用户名不存在和密码错，返回同一句"用户名或密码错误"**。这是故意的——避免坏人用不同报错来试探"哪个用户名存在"。

**刷新保持登录 `auth/me/route.ts`**：前端刷新页面后，用本地存的 token 调这个接口，后端 `getCurrentUser` 解开 token 查库，返回最新用户信息（含角色）。这就是"刷新页面不丢登录态"的原理。

**改密码 `auth/change-password/route.ts`**：先验证"原密码对不对"，再写新哈希；新密码至少 6 位。

**发票列表/上传 `invoices/route.ts`**
- `GET`：从库里拿全部发票，按上传时间倒序。
- `POST`：接收 `multipart/form-data`（前端上传文件的标准格式），**服务端二次校验**（归属人必填、文件必传——不能只信前端），然后把文件**落盘**到 `backend/uploads/`，只把元数据（文件名、类型、路径等）写进 MySQL。

**发票详情/删除 `invoices/[id]/route.ts`**
- `GET`：查单条元数据。
- `DELETE`：删数据库记录 **同时**删本地文件（`unlink`），文件删失败只记录日志不阻断响应。

**发票文件预览 `invoices/[id]/file/route.ts`**：读本地文件，用 `new NextResponse(data, {headers})` **流式**返回，并带 `Content-Disposition: inline` 让浏览器直接预览而非下载。

**用户管理 `users/route.ts`**：`GET` 列表、`POST` 建普通用户，都先用 `requireAdmin` 把门——非管理员直接 403。管理员建的账号固定 `role: 'user'`，不开放建管理员。

**健康检查 `health/route.ts`**：最简单的接口，部署或联调时先打它确认"服务活着"。

### 4.4 `prisma/schema.prisma` —— 两张表

```prisma
model Invoice {
  id          String   @id @default(cuid())
  ownerName   String
  fileName    String
  fileType    String
  invoiceDate DateTime
  uploadedAt  DateTime @default(now())
  note        String?
  storagePath String
  @@map("invoices")
}
model User {
  id           String   @id @default(cuid())
  username     String   @unique
  name         String
  passwordHash String
  role         String   @default("user")   // 'admin' | 'user'
  createdAt    DateTime @default(now())
  @@map("users")
}
```
- `@id` 主键，`@default(cuid())` 自动生成唯一 ID。
- `@unique` 用户名唯一，不能重。
- `String?` 的 `?` 表示"可空"（备注允许为空）。
- `@@map("表名")` 指定数据库里真实的表名。

### 4.5 `prisma/seed.ts` —— 第一次就有管理员

```ts
await prisma.user.create({
  data: { username: 'admin', name: '超级管理员',
          passwordHash: await bcrypt.hash('123456', 10), role: 'admin' },
})
```
跑 `pnpm prisma db seed` 就会创建 `admin / 123456`。已存在则跳过。

- **`docker-compose.yml`**：一键起 MySQL 容器（root/caiwu123，库 caiwu，宿主端口 3307）。

## 第 5 章 一个请求是怎么跑完的（端到端）

### 5.1 登录流程

```
浏览器(输入 admin/123456)
   │  POST /api/auth/login
   ▼
前端 axios/fetch 发请求（路径写 /api/... 相对路径）
   │
   ▼
Vite 开发服务器(5173) 发现是 /api → 代理转发到 localhost:4000
   │
   ▼
Next.js 后端 login/route.ts
   ├─ prisma.user.findUnique 查用户
   ├─ bcrypt.compare 比对密码
   └─ jwt.sign 签发 token
   │
   ▼
返回 { token, user }
   │
   ▼
前端把 token 存进 localStorage，路由守卫放行进入系统
```

### 5.2 之后每次带 token

```
前端请求（带请求头 Authorization: Bearer <token>）
   ▼
后端接口调用 getCurrentUser(req)
   ├─ getBearer 取 token
   ├─ verifyToken 验 token
   └─ prisma.user.findUnique 查最新用户信息（含 role）
   ▼
执行业务逻辑并返回数据
```

### 5.3 上传发票流程

```
前端 FormData(ownerName + file) → POST /api/invoices
   ▼
invoices/route.ts
   ├─ 服务端校验（归属人、文件必填）
   ├─ 文件落盘 backend/uploads/inv-xxxx.pdf
   └─ prisma.invoice.create 写元数据到 MySQL
   ▼
返回创建好的记录（含 storagePath）
```

## 第 6 章 前后端怎么连起来（Vite 代理）

前端跑在 `5173`，后端跑在 `4000`，是两个不同"源"，浏览器有跨域限制。本项目用 **Vite 代理** 绕开：前端统一写相对路径 `/api/xxx`，Vite 在开发服务器里悄悄转发到 `4000`（见根目录 `vite.config.ts`）：

```ts
server: {
  proxy: { '/api': 'http://localhost:4000' }
}
```

所以**前端不用管跨域、不用配 CORS**，专心写业务。这也是为什么 `next.config.mjs` 里没配跨域——有代理兜着。

> 教材文档里写代理指向 `8787`（旧 mock 模式），但当前代码已对接真实后端（`4000`），**以代码为准**。

## 第 7 章 怎么把这个后端跑起来

详细步骤见根 `README.md`，这里给后端专属速查：

```bash
cd backend

# 3. 建表 + 灌初始数据
```

（没装 Docker / WSL 起不来的同学，可考虑把 Prisma 的 `provider` 从 `mysql` 改成 `sqlite`，彻底免数据库服务——本项目 schema 只用了 `String`/`DateTime`，可无损迁移。）

## 第 8 章 新手最容易踩的坑

1. **`DATABASE_URL` 端口填错**：Docker 映射的是 `3307`，不是 MySQL 默认的 `3306`。本项目 `.env` 已填对。
2. **改了 `schema.prisma` 没重新生成**：改完要 `pnpm prisma generate`（或 `db push` 会自动带）。
3. **`prisma` 命令报错说连不上库**：先确认 `docker compose up -d` 真的起了、MySQL 还在初始化（首次要等几秒）。
4. **`params` 忘了 `await`**：Next.js 15 里动态路由参数是 Promise，直接 `params.id` 会拿到一个 Promise 而非字符串。
5. **密码明文存库**：永远用 `hashPassword`，绝不放原密码。
6. **token 放敏感信息**：只放 `userId`/`role`，密码之类不要塞进去。
7. **只在前端校验**：上传发票时后端又校验了一遍——**服务端校验不可省**，前端校验只是体验。
8. **跨域自己配半天**：有 Vite 代理兜着，本项目不需要你配 CORS。

## 第 9 章 下一步可以学什么

- **Prisma 进阶**：`db migrate dev`（带版本管理的迁移）vs `db push`（直接同步）的区别。
- **JWT 原理**：token 为什么能防伪（签名）、为什么设置过期时间、怎么吊销。
- **文件上传安全**：限制文件类型/大小、病毒扫描、对象存储（OSS/S3）替代本地落盘。
- **权限模型**：从"admin/user 两级"扩展到 RBAC（基于角色的访问控制）。
- **部署**：`next build` + `next start`，MySQL 上云，反向代理（Nginx）。

把上面这些吃透，你就不只是"会跑"，而是真懂这个后端在干什么了。
